# Scan 0.9.0 (core, full)

Commit scanned: `edaed6f` (branch v090). Full scan (pre-1.0 candidate), not
incremental. Scope: all of `src/` except `src/deck/`: main, daemon, apply,
plan, persist, store, memory, migrate, modes, clip, theme, feature, setup,
tool, hypr, backend (+ hyprland, fake), brightness, audio, power, night,
uevent, events, doctor, commands, spec, model, error. Method: read every
file listed above plus `contrib/*.service` and `docs/protocol.md`; ran
`cargo clippy ... -W clippy::indexing_slicing` and classified all 75 hits.
No code was run against a live Hyprland; no tests were run (read-only scan).
`cargo audit` is not installed here, so it was not run.

Prior scans (0.3.0 to 0.8.0) were skimmed; nothing already fixed is
re-reported. The earlier fixes I touched still hold (symlink refusal in
`atomic_write`, O_NOFOLLOW on lock/blobs, link_host backslash rule,
`Entry::sane`, sensitive-state skip, 64 KiB caps).

No critical or high findings. The main risk is in the guardian: several
paths leave the screen changed with nothing scheduled to revert it.

## Findings

### C1 Medium: change applied, but guardian/pending can fail to be set up
`src/apply.rs:359-361` (`write_pending(&p)?`, `spawn_guardian(...)?`),
`src/apply.rs:520-541`.
After `execute()` has already changed the monitors, `apply()` writes
`pending.json` and spawns the guardian with `?`. If either fails, the error
is returned but nothing is reverted:
- `spawn_guardian` uses `std::env::current_exe()`. After a package upgrade
  while a long-running stance (daemon, panel-spawned) is alive, Linux returns
  `/usr/bin/stance (deleted)`, so the spawn fails with ENOENT. The monitors
  stay in the new (possibly unusable) mode, `pending.json` exists but no
  process will act on it.
- `write_pending` fails (disk full, state dir perms) and the change stays.
- SIGKILL/OOM of the stance process between `execute()` and `write_pending`
  has the same effect (no snapshot on disk at all).
Fix: on error after `execute`, run `execute_inner(before)` (or `restore`)
before returning. Better: write `pending.json` (snapshot) before `execute`,
and spawn the guardian before applying; clear them if the apply fails. Use
`/proc/self/exe` or strip the ` (deleted)` suffix and fall back to
`/usr/bin/stance`.

### C2 Medium: guardian exits on a single failed `version()` call
`src/apply.rs:451-453` (`if self.backend.version().is_err() { return Ok(()) }`).
`version()` goes through `Instance::request` with a 2 s I/O timeout and JSON
parsing. During a modeset Hyprland can stall for longer than 2 s, or return
a reply that does not parse; the guardian then concludes "compositor gone"
and exits permanently, exactly in the window where a bad mode needs
reverting. Nothing else reverts until some later `stance` command runs
`sweep` (and the daemon never sweeps). docs/protocol.md describes this
behaviour, so it is by design, but the trigger is too sensitive.
Fix: only treat the compositor as gone when the instance dir or socket file
has vanished (`!inst.dir.join(".socket.sock").exists()`) or after N
consecutive failures spanning at least ~5 s. At the deadline always attempt
the restore (it fails harmlessly with no compositor).

### C3 Medium (uncertain): guardian shares the caller's cgroup
`src/apply.rs:526-537` (`process_group(0)` only). A new process group does
not leave the systemd cgroup. When the panel runs as
`stance-panel.service` (`contrib/stance-panel.service`, default
`KillMode=control-group`), a Quickshell crash or `systemctl --user restart`
during the 12 s window kills the guardian. Quickshell crashing on an output
change is plausible, and that is exactly when the change was made from the
panel. Partial mitigation: the restarted panel's `stance status` runs
`sweep`, which reverts after deadline + 2 s, but only if the panel (or the
user) calls it. A CLI call from a bar `exec` in a transient scope is
unaffected.
Fix: spawn the guardian via `systemd-run --user --collect --quiet
--unit=stance-guardian-N` when `systemd-run` exists (absolute path through
`tool::find`), or have the daemon (when running) wake on `pending.json`
(inotify) and sweep after the deadline. Uncertain because I did not
reproduce a Quickshell crash.

### C4 Medium: a failed revert drops the snapshot
`src/apply.rs:~288-300` (`restore`): `self.clear_pending()` runs before the
result is examined. If both attempts fail (e.g. a mode that no longer
exists, IPC hiccup), `pending.json` and with it the only record of the old
state is deleted; the user only gets a notification (`RevertFailed`). No
later sweep or `stance revert` can retry.
Fix: keep the pending file (mark `failed: true`, so the panel stops the
countdown) or copy the snapshot to `state/last-revert-failed.json`; retry on
the next `sweep`.

### C5 Low-Medium: event socket reader exits on non-UTF-8 and loses partial lines
`src/backend/hyprland.rs:25-36` (`Socket2::next`, `read_line` into `String`).
Hyprland forwards window titles and classes in events (`activewindow>>`,
`windowtitle>>`) and does not guarantee UTF-8. `BufRead::read_line` returns
`InvalidData` for such a line; the code maps every non-timeout error to
`Err(ipc)`, `event_loop` returns it with `?`, and the daemon exits with
status 2. systemd restarts it (`Restart=on-failure`), and the restart
re-applies the matching rule at start (`hotplug_at = Some(now)`), which can
move screens the user just arranged by hand. Also, with the 1 s power-poll
timeout, a timeout in the middle of a line drops the bytes already read
(the `String` is a local), so the next read parses a tail as an event.
Fix: keep one `Vec<u8>` buffer across calls, use `read_until(b'\n')` and
`String::from_utf8_lossy`; on `WouldBlock` keep the partial bytes for the
next call. Cap the line length (e.g. 64 KiB).

### C6 Low: uevent watcher thread ends on ENOBUFS
`src/uevent.rs:38-47`. `recv` returns -1/ENOBUFS when the netlink receive
buffer overruns (a burst of uevents, e.g. a dock or many USB devices). Any
error except EINTR does `break`, the thread closes the fd and stops for the
rest of the process lifetime; `watch_power` already returned true so the
daemon keeps `power_poll = true` and believes it is watching. Power rules
then silently stop reacting to the charger.
Fix: `continue` on ENOBUFS, EAGAIN and ENOMEM; break only on EBADF/ENOTSOCK.
(Bounds: `&buf[..n as usize]` is guarded by `n >= 0` and `n <= buf.len()`.)

### C7 Low: `std::env::args()` panics on non-UTF-8 arguments
`src/main.rs:221`. A non-UTF-8 argv entry (file names passed to
`theme import`, `deck send`, `clip` ids from a script) aborts the process
(`panic = "abort"` in release) instead of returning a usage error. Not
reachable from the daemon/guardian (their argv is fixed).
Fix: `std::env::args_os()` and refuse or lossily convert with a `usage`
error.

### C8 Low (usability/robustness): group-writable refusal breaks UPG distros
`src/store.rs:44-50, 53-` (`check_dir`), `store.rs:~96-110` (`read_checked`),
`hypr::check_private_dir`. Directories and files with the group-write bit
are refused. On Fedora/Ubuntu-style user-private-group setups (umask 002)
`~/.config/hypr` is usually 0775 and editors create 0664 mode files, so
`stance persist` (writes into `~/.config/hypr` via `atomic_write` ->
`check_dir`), `stance mode save` into pre-existing dirs, and loading hand-
written mode/rules/theme files fail with `unsafe_path`. Not a vulnerability;
it fails closed. Fix: allow g+w when the file's group is the user's own
private group (gid == uid and sole member), or at least make the error name
the `chmod g-w` remedy; for `persist`, only require ownership of
`~/.config/hypr` (we do not store secrets there).

### C9 Low: unlocked read-modify-write (lost update only)
- `src/daemon.rs:~236` (`on_reload`) calls `memory::record` without the
  state lock while a concurrent CLI `apply()` writes `memory.json` under it
  (`src/memory.rs:84-125`): last writer wins, one remembered position lost.
- `src/modes.rs:~257-315` `save` / `save_rules`: `path.exists()` check then
  write with no lock; two concurrent saves (panel editor plus CLI) race, the
  `--force` check can be bypassed.
- `src/theme.rs:~384-415` `put`: `MAX_USER_THEMES` and `exists` checks are
  not atomic with the write.
- `src/brightness.rs:~270-285` `ddc.json` cache is atomic-write but unlocked
  (stale cache self-heals).
- `src/store.rs:~65` temp name is `.name.<pid>.tmp`; two threads of the
  daemon writing the same file (night.json thread and main loop) collide on
  `create_new` and one gets a spurious `io` error; a stale temp from a
  crashed process whose pid is reused blocks that file.
Fix: use `store::lock_named(config_dir, "config.lock")` around config
writers; add a per-call counter to the temp name.

### C10 Low: `theme export` not exclusive; `theme rm` cannot remove a broken theme
- `src/theme.rs:473-499` `export_to`: the existence check and the open are
  separate and the open is `create(true).truncate(true)` (no `create_new`).
  Without `--force`, a file that appears in between is truncated. The write
  is also not atomic (a crash leaves a partial file). Fix: `create_new(true)`
  when `!force`; temp file plus rename when `force`.
- `src/theme.rs:423-436` `rm` calls `self.get(id)?` first, so a user theme
  that fails validation (hand edit, newer fields) cannot be removed from the
  CLI. Fix: check existence with `symlink_metadata` instead of full parse.

### C11 Low (hardening): unchecked arithmetic on state-file values
All inputs are private, user-owned files (0600, owner checked), so this is
tamper/corruption hardening only; release builds wrap silently (no
`overflow-checks`), debug builds panic.
- `src/apply.rs` (`sweep`): `p.deadline_ms + SWEEP_GRACE_MS`; a
  `deadline_ms` near `u64::MAX` wraps and triggers an immediate revert.
  Also `p.generation + 1` at ~line 350.
- `src/clip.rs` `prune_index`: `idx.items.iter().map(|e| e.size).sum()`;
  `idx.next_id = id + 1` in `add`.
- `src/memory.rs:153-157`, `src/plan.rs:432-446, 523-531`: `b.x + bw`, `rs.x +
  rw` (i32; positions are bounded by `validate()` to 100 000 and sizes to
  about 65 536, so safe on the validated paths; `memory::recall` runs
  `validate()` first as well).
Fix: `saturating_add` / `checked_add` in those few spots.

### C12 Low: `doctor --report` includes local names
`src/doctor.rs:~365-430` (`shell_checks`) and `src/doctor.rs:~546`
(`clip_check`), `src/main.rs:1618-1674` (`bug_report`). The report is meant
to be pasted publicly. `$HOME` and `/run/user/<uid>` are redacted, but the
report still contains the names of the user's Quickshell config directories
(`~/.config/quickshell/<name>`, could be a handle or project name), the
path of a `corrupt-<unix time>` clip folder, and, when `XDG_*` points
outside `$HOME`, those full paths. Monitor connector names are fine
(`DP-1`); EDID description/serial and paired phone names are not included
(confirmed: only a device count). Fix: in `bug_report`, filter the `shell`
check id (or reduce it to `ii`/`end4-pC` flavor), and redact absolute paths
generally (replace any `/home/<x>` via regex, not just `$HOME`).

### C13 Info: serde error text can quote clipboard preview text
`src/clip.rs:~532` (`clip index: {e}`) and `clip.rs:~565` (`eprintln!` in
`mutate`). For a damaged or foreign index, `serde_json` type errors include
a snippet of the offending value (`invalid type: string "<preview>"`).
That text goes to stderr, hence the journal, and into `doctor` warnings.
Only on a damaged index, so low. Fix: print only `e.classify()` and the
line/column.

## Checked, clean

- Process spawning: every spawn site (`tool::run_tool`, `status_timeout`,
  `power::run`, `night::start`, `clip::copy`, `apply::spawn_guardian`,
  `feature`, `setup`) uses an argv list, `stdin(null)`, absolute paths from
  `tool::find` (name charset-checked, `/usr/bin` first, relative PATH
  entries ignored), no shell. `run_tool` has a hard timeout with kill and
  wait, caps stdout at 4 MiB and stderr at 64 KiB, and sanitizes stderr.
  `power::run` uses `.output()` without a timeout, but only for
  `powerprofilesctl get/set` with fixed arguments (hang risk only,
  informational). User text never becomes a flag: sink ids are numeric
  (`wpctl set-default <u32>`), brightness device/bus names are charset-
  validated, the clip mime passed to `wl-copy --type` is taken from the
  user-private index and is a value argument.
- Hyprland IPC: socket path from `XDG_RUNTIME_DIR` (absolute only) plus a
  signature restricted to `[A-Za-z0-9_-]` (256 max); dir checked owner/mode,
  socket checked with `lstat` (is_socket, owner). Replies capped at 4 MiB
  with 2 s I/O timeouts; malformed JSON gives an `ipc` error, not a panic.
  Everything interpolated into `eval`/`keyword`/`dispatch` strings passes
  `check_connector` (alnum, `-`, `_`), numeric fields, or fixed text, so no
  newline or Lua/hyprlang injection (also `persist` comments are single-line
  and descriptions are sanitized, tested).
- Path traversal: mode names, theme ids, clip ids, feature names and
  `Entry` sha/ext are validated before any join; `blob_path` falls back to a
  nonexistent name for unsane entries.
- Symlinks/TOCTOU: `atomic_write` refuses a symlink destination, uses
  `create_new` + 0600 + `O_NOFOLLOW` temp in a verified private dir, fsyncs
  file and dir, and renames; lock files and blobs use `O_NOFOLLOW`; the clip
  index is opened `O_NOFOLLOW`; `check_dir` uses `symlink_metadata`.
- Size caps: `read_checked` 64 KiB (+1 on read), clip index 64 MiB, clip
  text 256 KiB / image 32 MiB (drained, not buffered), `from_json` 64 KiB,
  migrate files 1 MiB, theme import 64 KiB, IPC 4 MiB, tool output capped.
  Config/mode/rules/theme/pending/active/night/features parsers use
  `deny_unknown_fields` or ignore only the documented future keys.
- State locking: `apply`, `confirm`, `revert`, `sweep`, `status` and the
  guardian restore all run under the state `flock`; the lock fd is
  close-on-exec so spawned children do not hold it; the daemon takes a
  separate non-blocking `daemon.lock`. The guardian re-reads `pending.json`
  under the lock and checks generation and session before restoring, so a
  late guardian cannot revert a newer or confirmed change; a snapshot from a
  previous Hyprland session is dropped, never applied.
- Revert completeness: restore filters unplugged monitors, retries once,
  verifies via `monitors all`, refuses to leave zero active screens
  (`check_result`), and `execute` rolls back to `before` when an apply step
  fails midway (see C1-C4 for the remaining gaps).
- Clipboard: only `CLIPBOARD_STATE=data` is stored (unset, `sensitive`,
  `clear`, `nil` are drained and dropped, so an old wl-paste fails closed);
  `enabled`, `paused_until`, and the per-type switches are checked per copy;
  an unreadable or corrupt `clip.json` yields defaults (off); non-UTF-8,
  NUL, empty, and `file://` copies are rejected; images are accepted only by
  magic bytes with the PNG header sanity-checked; previews strip
  bidi/zero-width characters; blob written before the index entry; `clip
  get` neutralizes terminal escapes on a tty; nothing in `ingest` logs
  content (only error text, see C13).
- Daemon loop: events are debounced, burst-limited (3 changes/30 s pauses
  rules for 60 s), power poll is bounded to 1 s wakeups, no busy loop on
  `Tick`; the closed socket exits 0 and a real error exits non-zero for
  `Restart=on-failure` (see C5 for one avoidable error). A pending user
  change suppresses rule application on hotplug.
- Netlink/uevent: used only as a wake-up flag; `SUBSYSTEM=power_supply`
  match is an exact field compare; message buffer 8 KiB with a bounds-safe
  slice.
- `doctor --report`: redacts `$HOME` and `/run/user/<uid>`, drops the
  instance and socket checks, contains no clipboard data, serials, mode
  names, or phone names (only counts). See C12 for the leftover.
- Panic safety: crate-level `deny` on `unwrap_used`, `expect_used`, `panic`,
  `todo`, `unimplemented`, `unreachable`; release builds use `panic =
  "abort"`; no reachable unwrap found in daemon, guardian or the core
  command paths. Remaining panic source is C7 (argv).
- `memory.json`, `active.json`, `pending.json`, `night.json` are 0600, in a
  0700 dir, and refuse foreign owner or g/o-writable files on read.
- Fake backend is reachable in release via `--backend fake` /
  `STANCE_BACKEND=fake` (env, user-controlled); it only touches its own state
  file (`STANCE_FAKE_STATE` or `<state>/fake.json`), so no finding.
