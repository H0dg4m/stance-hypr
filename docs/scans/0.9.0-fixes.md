## New findings

**N1 (medium) restore that cannot succeed now retries and notifies without bound.** apply.rs `restore` (~415-440) keeps pending on failure and sends `Notice::RevertFailed` each time; daemon.rs `Live::sweep` (~170) runs after every event-loop iteration, and `parse_event` turns every unrecognised Hyprland event (activewindow, workspace, ...) into `Next::Tick`, so it runs at compositor event rate (and at least every 5 s). Scenario: a change expires, the snapshot cannot be verified (monitor ignores the mode; the exact case C4 is about); `sweep` sees `now > deadline + 2 s`, calls `restore` (two `execute_inner` runs, 300 ms sleep, all under the state lock), fails, notifies, keeps pending; the next event repeats. Result: a notify-send per event/5 s, the lock held ~0.5 s each time (blocking `stance` commands and the guardian), and pending never clears until the user runs `revert` or `confirm`. Fix: remember a failed sweep (store `failed_at` in pending, or an in-memory `Instant` in `Live`) and retry at most every 30-60 s, notify once.

**N2 (low) daemon sweep drops another live session's pending change.** `Ctx::sweep` clears a pending whose `session != backend.session_id()`. The daemon now does this continuously (before: at start and on CLI calls). With two Hyprland sessions sharing the state dir, session B's daemon deletes session A's pending within 5 s; A's guardian sees no pending and exits, so A's unconfirmed change is never reverted. Pre-existing semantics, widened in reach. Also the daemon sweep does not send `Notice::Reverted`, so an expiry revert by the daemon is silent.

**N3 (low) `handshake_enter` leaks map entries when full.** net.rs ~134: `h.entry(ip).or_insert(0)` runs before the `total >= MAX_HANDSHAKES` test, so a refused IP leaves a `0` entry that `handshake_leave` never removes. An attacker cycling source addresses (IPv6) while the 4 slots are full grows the map without bound (slowly, ~tens of bytes per address). Fix: use `get(&ip)` for the check and insert only on success. Also the slot is released by a plain call, not a guard: a panic inside `noise::accept` or a failed `thread::spawn` would leak a slot for good (same as the old counter; an RAII guard would be sturdier).

**N4 (low) confirm and revert share the new action cap.** net.rs ~924: `presses.len() >= PRESSES_PER_S || jobs.open >= JOBS_MAX` answers `Ack{ok:false,"too fast"}` for `Confirm`/`Revert` too. With 4 slow actions queued (each up to 30 s, serial), a phone cannot confirm or revert a display change; the countdown then reverts it, so the failure mode is safe but surprising. Fix: let Confirm/Revert bypass `JOBS_MAX` (they are serialised on the same worker, or run them ahead).

**N5 (low) `stance deck test watch` and other test clients may now be cut after 20 s.** A client that never pings or sends `caps` gets `Bye idle` after `FIRST_FRAME`. fake.sh passes, so current scripted uses are shorter; a long manual `watch SECONDS` would end early. Document or have the test client ping.

**N6 (info)** tool.rs: the doc comment `/// Finds name at /usr/bin/...` now sits above `own_exe` (the new function was inserted between the comment and `find`); move it. `plain(body, 200)` in `notify_paired` can truncate the unpair hint for long phone names. `confirm` after a failed expiry restore now reports confirmed (pending kept) where it used to report "nothing pending"; acceptable, it clears the stuck state.
